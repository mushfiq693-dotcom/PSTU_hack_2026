2. CORE ENGINEERING PILLARS (JUDGING CRITERIA DEFENSE)
--------------------------------------------------------------------------------
Pillar A: Double-Entry Ledger Pattern (Financial Standard)
  - Every money movement produces TWO immutable ledger entries:
      1. DEBIT: Deducts from Sender Account
      2. CREDIT: Adds to Receiver Account
  - Invariant: SUM(Debit) - SUM(Credit) = 0 across the entire system.
  - User wallet balance is a cached projection of the immutable ledger history.

Pillar B: Concurrency & Race Condition Defense (ACID Guarantees)
  - Uses SQLite in WAL (Write-Ahead Logging) mode with `BEGIN IMMEDIATE` transactions.
  - Locks sender & receiver balances in consistent order to prevent deadlocks.
  - Guarantees that even if 50 concurrent transfer requests hit an account with
    only BDT 1,000 simultaneously, exactly 1 will succeed and 49 will safely fail
    with zero balance discrepancy.

Pillar C: Network Resilience & Idempotency Engine
  - Every mutation request accepts an `Idempotency-Key` HTTP Header.
  - If a user rapidly taps "Send Money" or their mobile connection retries,
    the server detects the duplicate key and returns the original transaction
    receipt without executing a second debit.

Pillar D: Risk, Velocity & Limits Enforcement
  - Per-transaction and daily volume limits (e.g., max BDT 50,000 single transfer).
  - Velocity checks preventing rapid bot-like spamming.

Pillar E: The "Judge Magnet" Concurrency & Resilience Studio
  - A visual interactive dashboard where judges can click "Simulate 20 Concurrent
    Transfers" with a single click and watch live transaction safety & ledger
    verification graphs.

3. DATABASE SCHEMA & ENTITY RELATIONSHIPS
--------------------------------------------------------------------------------

[Users]
  - id (UUID / PK)
  - name (String)
  - phone (String, Unique)
  - email (String, Unique)
  - avatar (String)
  - pin (Hashed String)
  - created_at (DateTime)

[Wallets]
  - id (UUID / PK)
  - user_id (FK -> Users.id)
  - currency (Default "BDT")
  - balance (Decimal / Integer in Cents to avoid floating point errors)
  - status (ACTIVE, FROZEN)
  - updated_at (DateTime)

[Transactions] (High-level business record)
  - id (UUID / PK)
  - reference_id (String, Unique e.g. "TXN-2026-XXXX")
  - sender_wallet_id (FK -> Wallets.id)
  - receiver_wallet_id (FK -> Wallets.id)
  - type (TRANSFER, REQUEST_SETTLEMENT, BILL_SPLIT, INITIAL_SEED)
  - amount (Decimal)
  - fee (Decimal, default 0)
  - note (String)
  - category (General, Food, Rent, Entertainment, Utility)
  - status (SUCCESS, FAILED, PENDING)
  - idempotency_key (String, Unique nullable)
  - created_at (DateTime)

[LedgerEntries] (Immutable Double-Entry records)
  - id (UUID / PK)
  - transaction_id (FK -> Transactions.id)
  - wallet_id (FK -> Wallets.id)
  - entry_type (DEBIT / CREDIT)
  - amount (Decimal)
  - balance_after (Decimal)
  - created_at (DateTime)

[MoneyRequests] (P2P Invoices)
  - id (UUID / PK)
  - requester_id (FK -> Users.id)
  - payer_id (FK -> Users.id)
  - amount (Decimal)
  - note (String)
  - status (PENDING, ACCEPTED, DECLINED, CANCELLED)
  - transaction_id (FK -> Transactions.id, Nullable)
  - created_at (DateTime)
  - resolved_at (DateTime, Nullable)

[BillSplits] (Multi-party expense sharing)
  - id (UUID / PK)
  - creator_id (FK -> Users.id)
  - title (String, e.g. "PSTU Hackathon Lunch")
  - total_amount (Decimal)
  - split_type (EQUAL / EXACT)
  - status (ACTIVE, SETTLED)
  - created_at (DateTime)

[BillSplitItems]
  - id (UUID / PK)
  - bill_split_id (FK -> BillSplits.id)
  - user_id (FK -> Users.id)
  - share_amount (Decimal)
  - is_paid (Boolean)
  - paid_at (DateTime, Nullable)

[IdempotencyLogs]
  - key (String / PK)
  - user_id (FK -> Users.id)
  - response_status (Integer)
  - response_body (JSON / Text)
  - created_at (DateTime)

4. API SPECIFICATION & ROUTING
--------------------------------------------------------------------------------

Authentication & Users:
  - GET  /api/users                      -> List active users (for easy switcher)
  - GET  /api/users/me                   -> Current authenticated user & wallet
  - POST /api/users/switch/:id           -> Switch active demo user (instant demo)
  - POST /api/auth/register              -> Register new user (auto-seeds ৳100,000)

Wallet & Transfers:
  - GET  /api/wallet/summary             -> Balance, 24h spending, daily limit left
  - POST /api/transfers                  -> Execute atomic P2P transfer
         Headers: Idempotency-Key: <uuid>
         Body: { receiverPhone, amount, note, category, pin }
  - GET  /api/transfers/:id/receipt      -> Download/view cryptographic transfer slip

Money Requests (Invoicing):
  - GET  /api/requests                   -> List incoming & outgoing requests
  - POST /api/requests                   -> Create new money request
  - POST /api/requests/:id/accept        -> Atomically pay a pending request
  - POST /api/requests/:id/decline       -> Decline a pending request

Bill Splitter:
  - GET  /api/splits                     -> List user's active/past split bills
  - POST /api/splits                     -> Create multi-user split bill
  - POST /api/splits/:id/pay             -> Settle personal share atomically

Ledger & Analytics:
  - GET  /api/ledger/audit               -> Full double-entry balance check
  - GET  /api/analytics/insights         -> Spending by category, cashflow chart

Stress-Testing & Concurrency Lab:
  - POST /api/dev/stress-test            -> Triggers N concurrent transfers
         Body: { senderId, receiverId, count: 20, amountEach: 500 }
         Returns: { totalAttempts, succeeded, rejectedDueToBalance, durationMs, auditBalanceValid }

7. JUDGES DEFENSE & Q&A CHEAT SHEET
--------------------------------------------------------------------------------
Q1: "How do you guarantee that a user cannot double-spend by sending two requests simultaneously?"
A1: "We use atomic database transactions with SQLite's WAL mode and `BEGIN IMMEDIATE` locks.
     When a transfer initiates, the sender's balance is verified and debited inside an isolated
     transaction lock. Any concurrent thread is serialized or safely rejected if funds drop below
     the required amount."

Q2: "Why double-entry ledger instead of just updating a balance column?"
A2: "In real-world financial architectures, balance columns can suffer from data corruption or race
     drift. With double-entry bookkeeping, every transfer creates an immutable Debit and Credit entry.
     The balance is mathematically provable and can be reconciled at any millisecond."

Q3: "How does the system handle flaky mobile connections?"
A3: "Our client generates a unique Idempotency-Key for every transaction intent. If the client
     re-sends due to a timeout, our idempotency middleware returns the cached original result
     rather than executing a duplicate charge."

Q4: "How will this scale to 10M+ users?"
A4: "The architecture is modular with clean separation between the Ledger, Transfer Engine, and
     User Presentation layers. The schema supports horizontal sharding by wallet partition or
     migrating to PostgreSQL/CockroachDB with distributed row locks."
